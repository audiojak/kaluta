# tokio::process Asynchronous Command Execution: Child Process Standard Input Output Error

Status: proposed
Date: 2025-05-18
Deciders: Detection Pipeline (automated)

## Context

- External process execution is required across runtime routines, session interactions, and command invocation modules.
- Blocking process execution models risk exhausting the worker thread pool within an asynchronous runtime when external tools stall.
- Process invocations require standardized execution boundaries including timeout enforcement, signal handling, and buffered output capture.

## Problem Statement

Unsupervised or synchronous external process execution within an asynchronous runtime can block worker threads, cause thread starvation, and leave orphaned processes running indefinitely when external invocations hang or fail to terminate.

## Decision

1. MUST: Child process standard input, output, and error streams MUST be explicitly configured using standard process I/O descriptors to prevent unbuffered pipe deadlocks.

## Policy Block

- MUST Child process standard input, output, and error streams MUST be explicitly configured using standard process I/O descriptors to prevent unbuffered pipe deadlocks.

In scope:
- All internal workspace packages and modules executing external child processes or system tools.
- All asynchronous service routines managing interactive or background tool sessions.

Out of scope:
- Purely in-memory business logic and synchronous data parsing modules that perform no system process invocations.

Exceptions:
- EXC-20-001: Synchronous child process execution is permitted only in standalone test mock fixtures that run outside the asynchronous executor context.

## Rationale

- Evidence across multiple modules shows consistent adoption of tokio::process::Command integrated with tokio::time::timeout for robust sub-process supervision.
- Standardizing on asynchronous command abstractions prevents blocking calls from hindering runtime responsiveness during external tool runs.
- Mandating timeout wrappers guarantees determinism and fault isolation against hung or uncooperative external executables.

## Consequences

Positive:
- Non-blocking process execution prevents worker thread starvation across asynchronous execution contexts.
- Explicit timeout bounds eliminate hung or orphaned child processes during unresponsive tool or routine invocations.
- Consistent asynchronous process contracts provide standard lifecycle control across all agent interaction routines.

Negative:
- Asynchronous process management requires explicit cancellation handling to ensure sub-processes terminate upon parent task abortion.
- Standard input and output stream management demands careful buffer draining to avoid child process pipe saturation deadlocks.
- Additional testing complexity is required to simulate process timing variations and process termination signals.

## Alternatives

- Synchronous standard library process spawning inside background worker threads (rejected)
  Rejected because: Spawning dedicated threads for blocking process execution incurs unnecessary thread allocation overhead and fails to integrate cleanly with async cancellation and cooperatively scheduled timeouts.
  When valid: Valid only in single-threaded environments or standalone utility CLI tools lacking an asynchronous event loop.
- Unbounded asynchronous process execution without timeout supervision (rejected)
  Rejected because: Child processes that hang or stall can leak system process handles and indefinitely occupy asynchronous tasks, degrading service health.
  When valid: Valid only for perpetual supervisor daemon processes intended to run throughout the entire host application lifetime.

## Risks

- Child processes may ignore standard cancellation signals and continue running in the background.
  Mitigation: Implement cancellation grace intervals with escalation to termination signals to guarantee child process exit upon timeout.
  Owner: Engineering Team
- Large outputs generated by sub-processes can fill pipe buffers and deadlock child execution if unread.
  Mitigation: Configure standard output and standard error piping with asynchronous read streams or buffered output capture.
  Owner: Engineering Team

LOCK-VERSION GROUNDING (MANDATORY) — before writing code that uses a versioned library, execute in order:
1. Find the dependency manifest in the repo. It declares ranges, not installed versions.
2. Identify the build tool from the manifest.
3. Inspect the repository lock or resolution artifact to determine the exact resolved version. This artifact is authoritative; build-tool output only verifies the active environment matches it.
4. Look up the official documentation, changelog, or public API reference for that exact version. Do not use training-data recall — fetch or search the public internet for version-specific docs.
5. Confirm every API, class, or function you will call exists in that exact version's documentation before using it.
6. For version-sensitive behavior, re-run steps 3-5 per dependency at point of use.
- Ensure that any process kill signals allow for a graceful cancellation window before forcefully aborting stubborn processes.
- Always consume standard output and error asynchronously when capturing child output to avoid deadlock caused by full operating system pipe buffers.
